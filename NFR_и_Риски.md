# NFR и Риски для микросервисной архитектуры

## 5 тестируемых NFR для API GET /api/books

**Производительность.** 95 процентов запросов выполняются за 300 миллисекунд при одновременной нагрузке 100 запросов в секунду.

**Масштабируемость.** При увеличении нагрузки с 100 до 400 запросов в секунду добавление двух новых экземпляров сервиса сохраняет время ответа на уровне базовых 300 миллисекунд для 95 процентов запросов.

**Безопасность.** API возвращает только те книги, которые доступны текущему авторизованному пользователю. При отсутствии авторизации или роли User возвращается ошибка 401 или 403. Данные других пользователей не раскрываются.

**Отказоустойчивость.** При падении одного из трех экземпляров сервиса API продолжает обрабатывать запросы с оставшимися экземплярами. Доступность метода сохраняется на уровне 99.9 процентов.

**Надежность данных.** API возвращает актуальные данные из базы с задержкой не более одной секунды от момента изменения. При сбое реплики базы данных ответ формируется из другой реплики с тем же уровнем точности.

## 3 технических риска для микросервисной архитектуры соцсети для кошек

### Риск 1. Каскадный отказ

Один медленный сервис например рекомендации может затормозить сервис ленты, который ждет ответа, а затем падает вся система.

**Митигация.** Паттерн Circuit Breaker предохранитель. Сервис ленты перестает вызывать проблемный сервис после нескольких ошибок и показывает ленту без рекомендаций.

### Риск 2. Рассинхрон данных

Один и тот же фрагмент данных например имя пользователя хранится в нескольких сервисах профили и посты и расходится со временем.

**Митигация.** Паттерн Saga. Обновление проходит через цепочку событий через брокер сообщений. Все сервисы обновляют данные или откатывают изменения, полуобновленного состояния не бывает.

### Риск 3. Сложность отладки

Один запрос проходит через много сервисов. Понять какой из них тормозит без специальных инструментов почти невозможно.

**Митигация.** Распределенный трейсинг с корреляционным ID для каждого запроса. Все логи собираются в одну систему Jaeger или Zipkin, где видна полная картина пути запроса и времени в каждом сервисе.
