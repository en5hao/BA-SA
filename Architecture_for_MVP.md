# Архитектура для MVP социальной сети для кошек
## Проблема
Проект представляет собой социальную сеть для любителей кошек. В команде три разработчика. На создание MVP выделено всего три месяца. Главная цель как можно быстрее выйти на рынок и проверить гипотезу. Передо мной стоит выбор между монолитом и микросервисами.

### Микросервисная архитектура

Микросервисная архитектура дает возможность масштабировать отдельные функции независимо, переписать один сервис на другом языке и внедрять новую функциональность без остановки всей системы.

Однако она требует гораздо больше инфраструктуры, включает в себя API Gateway, оркестрацию сервисов и обмен сообщениями. Развертывание и отладка становятся сложнее. Каждый сервис нужно мониторить отдельно. Распределенные транзакции это отдельная головная боль. Базовая настройка такой архитектуры отнимет несколько недель.

### Монолитная архитектура

Монолитная архитектура это один код, одна база, одно развертывание. Разработка и отладка просты. Нет сетевых задержек между модулями. Легко делать сквозные изменения. Инфраструктурного кода требуется гораздо меньше. Один разработчик может понимать всю систему целиком.

Но монолит трудно масштабировать под отдельные функции. Любое изменение требует перезапуска всего приложения. Технологический стек будет единым для всех.

## Решение

Я выбираю монолит. Три разработчика это очень маленькая команда. Каждый человек очень важен. В микросервисной архитектуре один разработчик неизбежно займется только инфраструктурой, настройкой Kubernetes, API Gateway, сервисной сетки, мониторинга и трейсинга. Это займет минимум месяц из трех.
В монолите вся команда с первого дня пишет фичи. Через две недели уже можно показывать работающий прототип. Три месяца это жесткий срок, а микросервисы не дают преимущества на старте. Они дают преимущество когда у тебя 300 разработчиков и 30 миллионов пользователей. На старте у нас всего три человека и несколько сотен первых пользователей.
MVP не требует высокой доступности и горизонтального масштабирования. Даже если монолит упадет на пять минут, пользователи не заметят. Социальная сеть для любителей кошек это простая предметная область. Можно выделить модули прямо внутри кода, не вынося их в отдельные сервисы.

## План развития

Монолит сегодня не означает монолит навсегда.

**Первый этап. Чистый монолит.** Одна база кода. Модули разбиты по бизнес доменам. Нет прямого доступа к данным друг друга.

**Второй этап. Модулярный монолит.** Отдельные пакеты с четкими интерфейсами. Каждый модуль собирается в библиотеку. Коммуникация через вызовы методов.

**Третий этап. Выделение сервисов.** Когда команда вырастет до десяти человек, выделяем в отдельный сервис например профили. Остальное остается в монолите.

**Четвертый этап. Полная микросервисная архитектура.** Лента постов, уведомления, обмен сообщениями, медиа хранилище, рекомендации. У каждого сервиса своя команда.

## Вывод

Для стартапа с тремя разработчиками и тремя месяцами на MVP монолит это единственное разумное решение. Микросервисы убьют проект на старте. Они потребуют времени и ресурсов, которые не окупятся для первой версии продукта.

Правильная стратегия простая. Сделать быстрый монолит. Проверить гипотезу. Получить первых пользователей. А потом уже рефакторить и разделять, когда станет действительно трудно. Главное заложить правильные модульные границы внутри монолита, чтобы разделение в будущем было безболезненным.
